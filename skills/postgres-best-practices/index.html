1. Schema Design

Naming conventions

  • Use snake_case for all identifiers — tables, columns, indexes, constraints
  • Table names should be plural (users, projects, api_keys) — pick one convention and enforce it project-wide
  • Boolean columns: prefix with is_, has_, or can_ (is_active, has_verified_email)
  • Timestamp columns: suffix with _at (created_at, updated_at, deleted_at)
  • Foreign keys: <referenced_table_singular>_id (user_id, project_id)

Data types — use the right type

NeedUseAvoid
Primary keyuuid v7 (time-ordered) or bigserialuuid v4 (random — B-tree page splits), serial (32-bit overflow)
Variable texttextvarchar(255) — no perf benefit, arbitrary limits cause bugs
Money / financialnumeric(precision, scale)float / double precision — rounding errors
Timestampstimestamptztimestamp without tz — silently drops timezone
IP addressesinettext — inet supports indexing & range queries
JSON datajsonbjson — jsonb is binary, indexable, supports containment ops
Enumstext + CHECK or Postgres ENUMFree-form text with no validation
Yes/No flagsbooleansmallint or char(1)

Use Postgres native types instead of text

Postgres has purpose-built types that give you validation, indexing, and operators for free. Storing structured data as text throws all of that away.

DataNative typeWhat you get over text
IP addressesinetRange queries, containment checks, rejects invalid IPs
CIDR blockscidrNetwork containment, subnet math
MAC addressesmacaddrVendor prefix lookups, canonical formatting
Date rangesdaterange, tstzrangeOverlap (&&), containment (@>), exclusion constraints
DurationsintervalArithmetic (now() + interval '30 days'), comparison
CoordinatespointDistance calculations, GiST indexing
Case-insensitive textcitext (extension)Equality without lower() everywhere, indexable
 
-- Bad: stored as text, no validation, can't do range queries
ALTER TABLE audit_log ADD COLUMN ip_address text;

-- Good: validated on insert, supports subnet queries
ALTER TABLE audit_log ADD COLUMN ip_address inet;

-- Now you can query: "all requests from 10.0.0.0/8"
SELECT * FROM audit_log WHERE ip_address << '10.0.0.0/8';

When in doubt, check if Postgres has a type for it before defaulting to text.

Constraints — be explicit

  • Every table should have a primary key
  • Add NOT NULL to every column that should never be null
  • Use CHECK constraints for data-level business rules
  • Use UNIQUE constraints (not just unique indexes) for uniqueness rules
  • Always name your constraints explicitly
ALTER TABLE orders ADD CONSTRAINT positive_amount CHECK (amount > 0);
ALTER TABLE users ADD CONSTRAINT valid_email CHECK (email ~* '^.+@.+\..+$');

Default values

  • created_at → DEFAULT now()
  • updated_at → DEFAULT now() (update via trigger or app code)
  • UUIDs → prefer UUIDv7 (time-ordered) over v4 (random). v7 embeds a millisecond timestamp so new rows append to B-tree indexes instead of random page splits. Generate in application code (most languages have v7 libraries) or use the pg_uuidv7 extension (DEFAULT uuid_generate_v7()). Fallback: gen_random_uuid() generates v4 (built-in since Postgres 13).
  • Note: UUIDv7 leaks creation time in the ID — don't use as secret tokens
  • Boolean flags → explicit DEFAULT false or DEFAULT true, never leave nullable

Normalize repeatable concepts into related tables

When a column is likely to need multiple instances or new "kinds" over time, use a related table instead of adding more columns.

Rule of thumb If you're tempted to add a number suffix or type prefix to a column name (phone_1, address_billing, email_secondary), it should probably be a separate table.

Bad — numbered columns that grow with requirements and leave nulls everywhere:

ALTER TABLE users ADD COLUMN phone_home text;
ALTER TABLE users ADD COLUMN phone_work text;
ALTER TABLE users ADD COLUMN phone_mobile text;

Good — a related table where new kinds are just rows:

CREATE TABLE phone_numbers (
  id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  user_id uuid NOT NULL REFERENCES users(id),
  type text NOT NULL CHECK (type IN ('home', 'work', 'mobile', 'fax')),
  number text NOT NULL,
  is_primary boolean NOT NULL DEFAULT false,
  created_at timestamptz NOT NULL DEFAULT now()
);
CREATE INDEX idx_phone_numbers_user_id ON phone_numbers(user_id);

Applies to: phone numbers, emails, addresses, notes, tags, attachments, links — any concept where "how many" or "what kinds" may grow.

When columns are fine: the thing is truly singular and always present (created_at, email as login identifier), or there's a small, fixed set that will never grow.

Foreign key delete behavior — be intentional

Every foreign key should have an explicit ON DELETE action. Think about each relationship:

ActionWhen to useExample
RESTRICT / NO ACTIONSafe default — forces app to handle deletions explicitlyDeleting a user with active orders should fail
CASCADEChild rows are meaningless without the parentproject_members, join tables, per-parent settings
SET NULLChild should survive, reference is optionalassigned_to, created_by audit fields
 
-- CASCADE: members are meaningless without the project
ALTER TABLE project_members
  ADD CONSTRAINT project_members_project_id_fk
  FOREIGN KEY (project_id) REFERENCES projects(id) ON DELETE CASCADE;

-- SET NULL: tasks survive if the assigned user is deleted
ALTER TABLE tasks
  ADD CONSTRAINT tasks_assigned_to_fk
  FOREIGN KEY (assigned_to) REFERENCES users(id) ON DELETE SET NULL;
Anti-patterns Blindly using CASCADE everywhere (silent mass deletion) or never using it (orphaned junk data). Also: using CASCADE on tables that use soft deletes is contradictory — parent is soft-deleted but children are hard-deleted.

Don't store what you can compute

Never store values that can be derived from existing data — they go stale the moment they're written.

These columns are wrong the moment they're saved age (wrong on next birthday), full_name (drifts if name changes), days_since_signup (wrong tomorrow), order_total (drifts if line items are edited).

Store the source of truth, compute when needed:

-- Store date_of_birth, compute age at query time
SELECT date_part('year', age(date_of_birth))::integer AS age FROM users;

-- Store first_name and last_name, concatenate when needed
SELECT first_name || ' ' || last_name AS full_name FROM users;

-- Compute order total from line items
SELECT order_id, sum(quantity * unit_price) AS total
FROM order_items GROUP BY order_id;

If you need it indexed or queried often, use a generated column (Postgres 12+) — computed automatically, always in sync:

ALTER TABLE users ADD COLUMN full_name text
  GENERATED ALWAYS AS (first_name || ' ' || last_name) STORED;

Exception: pre-computed aggregates are acceptable for performance (e.g., comment_count on a post) — but only with triggers or app logic keeping them in sync, and only when the compute-on-the-fly cost is proven to be a problem.

Soft deletes

  • Use a deleted_at timestamptz column (null = not deleted)
  • Add a partial index for common queries:
CREATE INDEX idx_users_active ON users(id) WHERE deleted_at IS NULL;

Ensure all queries filter on deleted_at IS NULL unless intentionally querying deleted records.

2. Indexing Strategy

When to add indexes

  • Every foreign key column — Postgres does not auto-index foreign keys
  • Columns in frequent WHERE, JOIN, ORDER BY, or GROUP BY clauses
  • Columns used in uniqueness checks

Index types

ScenarioIndex Type
Equality / range queriesB-tree (default)
Full-text searchGIN on tsvector
JSONB containment (@>, ?)GIN on jsonb
Geometric / spatialGiST
Low-cardinality on large ordered tablesBRIN

Partial indexes

Use when you only query a subset of rows:

-- Only index active users — smaller, faster
CREATE INDEX idx_users_active_email ON users(email) WHERE deleted_at IS NULL;

-- Only index incomplete orders
CREATE INDEX idx_orders_pending ON orders(created_at) WHERE status = 'pending';

Composite indexes

  • Column order matters: most selective (highest cardinality) column first
  • Index on (a, b, c) serves queries on (a), (a, b), (a, b, c) — but not (b, c) alone
  • Don't create single-column indexes that duplicate the leading column of an existing composite

Anti-patterns

Over-indexing Every index slows writes. Audit unused indexes periodically. 
SELECT schemaname, relname, indexrelname, idx_scan
FROM pg_stat_user_indexes
WHERE idx_scan = 0
ORDER BY pg_relation_size(indexrelid) DESC;
  • Indexing boolean columns alone — too low cardinality. Combine with other columns or use a partial index.
  • Missing foreign key indexes — causes slow DELETE cascades and slow JOINs.

3. Query Performance

Use EXPLAIN ANALYZE

EXPLAIN (ANALYZE, BUFFERS, FORMAT TEXT) SELECT ...;

Red flags in query plans:

  • Seq Scan on large tables — usually a missing index
  • Nested Loop with high row counts — consider Hash Join or add an index
  • Sort with external merge Disk — work_mem too low or missing index
  • Rows estimated vs actual differ by 10x+ — run ANALYZE on the table

N+1 query detection

Look for patterns where the app fetches a list, then makes a separate query per row.

Fix Use JOIN, subquery, or WHERE id = ANY($1::uuid[]) to batch lookups.

Query anti-patterns

Anti-patternProblemFix
SELECT *Fetches unnecessary columns, prevents index-only scansSpecify columns explicitly
LIKE '%term%'Leading wildcard prevents index usepg_trgm + GIN index
NOT IN (subquery)Breaks with NULLs, can be slowUse NOT EXISTS
ORDER BY RANDOM()Scans entire tableTABLESAMPLE or offset approach
Unbounded queriesCan return millions of rowsAlways add LIMIT
 
-- Bad: NOT IN with NULLs
SELECT * FROM users WHERE id NOT IN (SELECT user_id FROM banned_users);

-- Good: NOT EXISTS
SELECT * FROM users u
WHERE NOT EXISTS (SELECT 1 FROM banned_users b WHERE b.user_id = u.id);

Pagination

Avoid OFFSET pagination on large datasets LIMIT 20 OFFSET 10000 still scans and discards 10,000 rows.

Use cursor/keyset pagination instead:

-- First page
SELECT * FROM items
WHERE tenant_id = $1
ORDER BY created_at DESC, id DESC
LIMIT 20;

-- Next page (pass last row's created_at and id)
SELECT * FROM items
WHERE tenant_id = $1 AND (created_at, id) < ($2, $3)
ORDER BY created_at DESC, id DESC
LIMIT 20;

4. Operational Best Practices

Connection pooling

  • Never allow unlimited connections — Postgres forks a process per connection
  • Use PgBouncer or your ORM's built-in pool
  • Small app: 10–20 connections. Medium: 20–50.
  • Set statement_timeout to prevent runaway queries:
ALTER ROLE app_user SET statement_timeout = '30s';

Transactions

  • Keep transactions short — long transactions hold locks and block autovacuum
  • Never hold a transaction open while waiting for user input or external APIs
  • Use READ COMMITTED (default) unless you specifically need stronger isolation
  • Wrap multi-step writes in explicit transactions

Vacuuming and maintenance

Never disable autovacuum It prevents table bloat and keeps query planner statistics current.

For tables with heavy UPDATE/DELETE churn:

ALTER TABLE hot_table SET (
  autovacuum_vacuum_scale_factor = 0.05,    -- default 0.2
  autovacuum_analyze_scale_factor = 0.02    -- default 0.1
);

Monitor dead tuples:

SELECT relname, n_dead_tup FROM pg_stat_user_tables ORDER BY n_dead_tup DESC;

Migrations

  • Always run migrations in a transaction
  • ADD COLUMN with DEFAULT is safe in Postgres 11+ (no table rewrite)
  • Use CREATE INDEX CONCURRENTLY to avoid locking the table (cannot run inside a transaction)
  • Renaming columns: add new → backfill → deploy code → drop old
  • Dropping columns: stop reading the column before dropping it

Backups

  • pg_dump for logical backups (portable, per-database)
  • WAL archiving + pg_basebackup for point-in-time recovery
  • Test your restores — an untested backup is not a backup
  • Railway provides daily snapshots; for critical data, also set up external backup to S3 or similar

Monitoring

Key metrics to watch:

MetricTarget
Cache hit ratio> 99%
Active connectionsWell under max_connections
Dead tuplesAutovacuum keeping up
Long-running queriesNone > 30s (investigate if so)
 
-- Cache hit ratio (should be > 99%)
SELECT sum(heap_blks_hit) / (sum(heap_blks_hit) + sum(heap_blks_read)) AS cache_hit_ratio
FROM pg_statio_user_tables;

-- Long-running queries
SELECT pid, now() - query_start AS duration, query
FROM pg_stat_activity
WHERE state != 'idle' AND now() - query_start > interval '30 seconds'
ORDER BY duration DESC;

5. Security

Roles and privileges

Never use the postgres superuser for application connections. 
CREATE ROLE app_user LOGIN PASSWORD 'strong-password-here';
GRANT CONNECT ON DATABASE mydb TO app_user;
GRANT USAGE ON SCHEMA public TO app_user;
GRANT SELECT, INSERT, UPDATE, DELETE ON ALL TABLES IN SCHEMA public TO app_user;
ALTER DEFAULT PRIVILEGES IN SCHEMA public
  GRANT SELECT, INSERT, UPDATE, DELETE ON TABLES TO app_user;
  • For read-only services: separate role with only SELECT
  • Revoke CREATE on public schema from PUBLIC (Postgres 15+ does this by default)

SQL injection prevention

  • Always use parameterized queries — never concatenate user input into SQL
  • For dynamic ORDER BY, whitelist allowed column names:
const ALLOWED_SORT_COLUMNS = ["created_at", "name", "status"];
if (!ALLOWED_SORT_COLUMNS.includes(sortBy))
  throw new BadRequestException("Invalid sort column");

Row-Level Security (RLS)

Defense-in-depth for multi-tenant apps:

ALTER TABLE projects ENABLE ROW LEVEL SECURITY;

CREATE POLICY tenant_isolation ON projects
  USING (tenant_id = current_setting('app.current_tenant_id')::uuid);

-- Set per-request in your application:
SET LOCAL app.current_tenant_id = 'tenant-uuid-here';

Not a replacement for app-level tenant filtering, but prevents data leaks if app code has a bug.

SSL / TLS

  • Always connect with SSL in production — sslmode=require (or verify-full for mutual TLS)
  • Railway and most managed providers enforce SSL by default

Secrets management

  • Never commit database credentials to version control
  • Use environment variables or a secrets manager
  • Rotate credentials after any team member offboarding

6. Audit Checklist

Schema

  • All tables have explicit primary keys
  • No varchar(255) — using text instead
  • Using timestamptz not timestamp for all time columns
  • Using numeric not float for money/financial values
  • Using jsonb not json for JSON columns
  • All non-nullable columns have NOT NULL
  • Foreign keys have explicit constraint names
  • Boolean columns have explicit defaults

Indexes

  • Every foreign key column is indexed
  • No unused indexes (check pg_stat_user_indexes)
  • Partial indexes used where appropriate
  • No duplicate indexes (single-column duplicating composite prefix)

Queries

  • No SELECT * in application code
  • No N+1 query patterns
  • All user-facing queries have LIMIT
  • No NOT IN (subquery) — using NOT EXISTS
  • Large-table pagination uses cursor/keyset, not OFFSET

Operations

  • Connection pooling configured with bounded pool size
  • statement_timeout set on the application role
  • Autovacuum is enabled
  • Migrations use CREATE INDEX CONCURRENTLY
  • Backup strategy exists and restores tested

Security

  • App connects with a dedicated role, not postgres
  • All queries use parameterized inputs
  • SSL enforced on production (sslmode=require)
  • Credentials in env vars, not in code
  • CREATE on public schema revoked from PUBLIC
